# Build coordination comparison — 7 November 2026

This compares the local Appling source with my_editor and the observed social-media run. It does not establish that Appling has passed the same project or that either product can build arbitrary applications without failures. No application source was manually changed during this investigation.

| Area | Appling evidence | my_editor finding and response |
|---|---|---|
| Work ownership | `plugins/ultimate-builder/skills/app-it/SKILL.md`, “Solve problems” and “Run the work”: a coordinator routes approved tasks and repairs to development; each handoff includes owned files, project memory and verification commands. | Previously, a single-file worker could identify a defect in another file but could not schedule its repair. Releases 0.0.63–64 added a durable queue, exact decision reuse and explicit review of new supporting files. Writes remain one file at a time. |
| Dependency scheduling | `task-planner/SKILL.md`, steps 5–6: tasks declare consumed/produced interfaces and form a dependency graph. | The live routes repair requested the unimplemented publish service. Normal module ordering changed, but the repair queue still selected routes. Release 0.0.65 schedules prerequisites in the active queue too and recovers an older recorded-but-unscheduled request. |
| Contract consistency | `sw-architect/SKILL.md` and `task-planner/SKILL.md`: exact types, field names, paths and public interfaces are part of planning. | The saved application plans left ID representation unspecified; separate generated implementations chose incompatible types. The user selected integer IDs. Future architecture/flow prompts now explicitly require ID ownership, exact shared types and producer/consumer agreement. Existing saved plans are not silently rewritten. |
| Verification | `sw-developer/SKILL.md`, steps 2b–2f and Fix mode: run tests, lint, production build and reproductions; do not equate generated code with verified behavior. | The user's selected workflow deliberately builds first, then tests and QA. File counts are implementation progress, not passing tests. A 0.0.65 regression ensures ending the build in a repair queue still reaches tests and QA. Production startup/browser acceptance remains a separate verification obligation; the current application has not yet passed it. |
| Bounded continuation | `tools/delegate_tool.py`, `_run_child_to_completion`: continue an unfinished task with its history for a bounded number of rounds. | my_editor bounds tool calls and performs protocol/decision recovery, but has no equivalent general continuation coordinator. Blindly retrying every BLOCKED result would conceal unresolved decisions and repeat failed work. The observed scheduling loop is fixed at its cause. |
| Activity and stalls | `web/src/lib/guided-turn-watchdog.ts`: distinguish model, tool and worker inactivity; explain the specific timeout. | my_editor's CLI request has a ten-minute total timeout and limited activity events. A quiet Codex reply can look stuck while preparing code. This remains a visibility/recovery limitation; 0.0.65 does not claim to replace its provider watchdog. |

Appling also varies planning depth by an explicit build profile and uses task-sized work, sometimes concurrently. The original one-file sequence incurred more model round trips. After the user explicitly relaxed that requirement, 0.0.66 added optional batches of up to three same-module files, retaining separate validated saves and summaries. Its project brain supplies context; it cannot compensate for missing design decisions or a controller that schedules the wrong file.

## Verification of the scheduler fix

- Unit coverage: prerequisite priority, preservation of the approved decision, existing consumer repairs, duplicate pending work, old unscheduled requests, cycles, actual repeated requests and scope boundaries.
- Real-editor coverage: new migration approval/cancellation; one-file saves; pause/resume without late writes; a repair requesting the original blocked file as a prerequisite; return to its consumer; unique progress counts; transition to tests and QA after the last repair.
- Live acceptance is recorded in `progress.md`. Application generation and saving are performed through my_editor itself.
